# 题目更新维护指南

这份文档给知识库维护者使用，不在网站导航中展示。题目原文位于 `content/questions/`；改动合并到 GitHub 仓库的 `main` 分支后，网站会自动重新构建，不需要在网站后台再录入一次。

## 修改已经发布的题目

1. 从[题目索引](../README.md#题目索引)找到题号，打开对应 Markdown 文件。也可以在网站题目页点击“编辑题目”，直接进入 GitHub 编辑界面。
2. 只修正需要改动的字段或题面。中英文任一版本发生变化时，核对另一版本的数字、条件、定义、小问和公式。保留 `<details>` 中的完整英文原题。
3. 题号 `id` 和文件夹不要改名。它们决定网页链接，也被已有解答引用。若原题确实需要重大改写，应在合并请求中解释缘由，并检查现有解答是否仍适用。
4. 点击 GitHub 的提交按钮，创建分支和合并请求。描述改动原因、依据及对中英文版本的核对结果。检查通过、审阅后合并。

如果只是调整难度或主题，修改文件头中的 `difficulty`、`category`、`tags` 即可；页面筛选和分类数量会随构建自动更新。

## 增加下一周的题目

以第三周第一题为例：

1. 新建目录 `content/questions/week-03/`。
2. 复制 [`templates/question.md`](../templates/question.md) 到 `content/questions/week-03/03-1-short-name.md`。文件名后半段用简短英文单词和连字符；题号 `03.1` 在仓库内保持唯一。
3. 填写文件头。`id: "03.1"`、`week: 3`、所在目录 `week-03` 三者必须对应。`date` 是该期发布月份，如 `"2026-10"`，不是自动生成的提交日期。
4. 写完整中文题面，再写完整英文题面。条件、符号、数值、胜负规则和所有小问都要一致。若引用外部题目，注明来源并确认有权分享。解答应放在 `content/solutions/03.1/` 的独立文件中，不写进题目正文。
5. 更新 [`README.md`](../README.md) 的题目索引，添加“第三周”和新题链接。网站首页的周数、归档、题目数量和筛选选项会自动更新。
6. 发起合并请求。GitHub Actions 会运行内容检查与网站构建；检查通过并合并后，Pages 会部署新版。

文件头的具体字段和允许值见 [`CONTRIBUTING.md`](../CONTRIBUTING.md#新增或修改题目)。如果想在本地预览，在仓库根目录运行 `npm ci`、`npm run check`、`npm run build`、`npm run dev`；只用 GitHub 网页提交内容时，不必安装 Node.js。

## 发布后检查

打开网站的周归档和新题链接，核对标题、周次、中文正文、展开后的英文、公式与表格，以及手机端显示。核对首页题目数量、分类和筛选选项。发现问题时继续修改原文件并提交，不要另建一个同题号文件。

目前没有官方标准答案。社区解答应以独立文件和署名保留，审阅时重点看假设、推导、验证和局限。不要凭投票结果直接修改题目难度；投票只是读者反馈，应与实际题目内容和审阅意见一起判断。

## 更新每周反馈投票

投票使用仓库的公开 [GitHub Discussions 投票分类](https://github.com/Praymo/qtia-open-quant-handbook/discussions/categories/polls)，不在网站中保存投票数据。新一期发布时，在该分类点击“New discussion”，分别创建难度、题量、答案与讲解三个单选投票。题目标题写清周次，避免不同期次混淆；检查选项后再发布，因为已经有人投票时不应随意改动选项含义。

创建完成后，记录每个讨论链接末尾的编号，修改 [`src/data/feedback.json`](../src/data/feedback.json) 的 `week`、三个 `discussion` 编号，以及相应文案与选项。合并后网站“反馈投票”页会指向新一期；旧投票和结果仍留在 GitHub Discussions 中。发布前逐个打开链接，确认投票问题、选项和“Show Results”结果入口正常。
