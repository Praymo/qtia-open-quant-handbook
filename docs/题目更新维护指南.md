# 题目更新维护指南

这份文档给知识库维护者使用，不在网站导航中展示。题目原文位于 `content/questions/`；改动合并到 GitHub 仓库的 `main` 分支后，网站会自动重新构建，不需要在网站后台再录入一次。

## 修改已经发布的题目

1. 从[题目索引](../README.md#题目索引)找到题号，打开对应 Markdown 文件。也可以在网站题目页点击“编辑题目”，直接进入 GitHub 编辑界面。
2. 只修正需要改动的字段或题面。中英文任一版本发生变化时，核对另一版本的数字、条件、定义、小问和公式。保留 `<details>` 中的完整英文原题。
3. 题号 `id` 和文件夹不要改名。它们决定网页链接，也被已有解答引用。若原题确实需要重大改写，应在合并请求中解释缘由，并检查现有解答是否仍适用。
4. 点击 GitHub 的提交按钮，创建分支和合并请求。描述改动原因、依据及对中英文版本的核对结果。检查通过、审阅后合并。

如果只是调整难度或主题，修改文件头中的 `difficulty`、`category`、`tags` 即可；页面筛选和分类数量会随构建自动更新。

## 第三周怎么上传：直接使用 GitHub 网页

下面以第三周第一题 `03.1` 为例。只需编辑 Markdown 文件，无需修改网站代码，也无需安装 Node.js。

1. 打开[仓库的题目目录](https://github.com/Praymo/qtia-open-quant-handbook/tree/main/content/questions)，点击右上角 **Add file → Create new file**。在文件名栏输入 `week-03/03-1-你的英文短文件名.md`，例如 `week-03/03-1-card-problem.md`。GitHub 会自动建立 `week-03` 文件夹。第二题改为 `03-2-xxx.md`、题号 `03.2`，以此类推。
2. 打开[题目模板](../templates/question.md)，复制全文到新文件。把 `title`、`titleEn`、`summary` 改成真实内容；保持 `id: "03.1"` 和 `week: 3`。`date` 填发布月份，例如 `"2026-09"`。`category` 只能填 `algorithm`、`probability` 或 `brainteaser`；`difficulty` 填 `D1` 至 `D5` 或 `Optional`；`tags` 暂时只填一个简短英文词；`contributors` 填实际贡献者的 GitHub 用户名。题号必须与 `week-03` 和文件名前缀对应。
3. 在 `## 中文题目` 下写完整中文题面；在 `<details>` 中写完整英文题面。核对两种语言的数字、条件、符号和每个小问。若引用外部题目，在文末注明来源并确认可以分享。不要在题目文件里放官方答案；社区解答单独存放在 `content/solutions/03.1/`。
4. 点击 **Commit changes...**，选择创建新分支，并发起 **Pull Request**。如果这一周有多道题，先把 PR 保持打开：回到该分支，按同样方法创建 `03-2-xxx.md` 等文件，它们会自动进入同一个 PR。
5. 在同一分支编辑 [`README.md`](../README.md) 的“题目索引”：参照第二周表格，新建“### 第三周”并加入每道题的链接，例如 `[题名](content/questions/week-03/03-1-card-problem.md)`。保存后也会进入同一个 PR。
6. 打开 PR 的 **Checks**，等待内容检查和构建通过；报错时点开日志，看它指出的文件和字段，修改同一分支后检查会重跑。核对题目后合并到 `main`。网站会自动部署，周次、题数和筛选项会从题目文件生成。

文件头的完整字段说明见 [`CONTRIBUTING.md`](../CONTRIBUTING.md#新增或修改题目)。在本地操作时，可运行 `npm ci`、`npm run check`、`npm run build`、`npm run dev` 预览；上传流程仍是把修改推送到分支、发起 PR、通过检查并合并。

## 发布后检查

打开网站的周归档和新题链接，核对标题、周次、中文正文、展开后的英文、公式与表格，以及手机端显示。核对首页题目数量、分类和筛选选项。发现问题时继续修改原文件并提交，不要另建一个同题号文件。

目前没有官方标准答案。社区解答应以独立文件和署名保留，审阅时重点看假设、推导、验证和局限。不要凭投票结果直接修改题目难度；投票只是读者反馈，应与实际题目内容和审阅意见一起判断。

## 更新每周反馈投票

投票使用仓库的公开 [GitHub Discussions 投票分类](https://github.com/Praymo/qtia-open-quant-handbook/discussions/categories/polls)，不在网站中保存投票数据。新一期发布时，在该分类点击“New discussion”，分别创建难度、题量、答案与讲解三个单选投票。题目标题写清周次，避免不同期次混淆；检查选项后再发布，因为已经有人投票时不应随意改动选项含义。

创建完成后，记录每个讨论链接末尾的编号，修改 [`src/data/feedback.json`](../src/data/feedback.json) 的 `week`、三个 `discussion` 编号，以及相应文案与选项。题目选项必须与 GitHub 上的投票逐字一致，网站才会显示结果。合并后网站“反馈投票”页会指向新一期；旧投票和结果仍留在 GitHub Discussions 中。GitHub Actions 在每次发布及约每小时一次的定时构建中读取票数，生成网站上的结果图表；无需手动更新票数。发布前逐个打开投票链接，并查看部署任务是否通过。
